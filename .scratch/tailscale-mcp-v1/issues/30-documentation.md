# 30 — Documentation

Status: done
Milestone: 5 — Packaging
Blocked by: 29

The README and the documentation folder: what the server is, install per channel, configuration by environment variable and flag, the tier and preset model with the listing counts, the tool table generated from the metadata table rather than written by hand, the error codes with their meanings, and the comparison table against the three reference implementations that names the four deliberate exceptions so that the superset claim is honest.

## Acceptance criteria
- The tool table is generated and a test fails when it is stale.
- Every environment variable and flag is documented, with defaults.
- The comparison table lists each reference implementation's features and marks the four exceptions explicitly.
- The security section states what the tiers do and do not protect against, and that the server never escalates privileges.

## As built

Four documents and one test file. The README is what somebody reads before
installing; `docs/` is what they read afterwards. Everything in either that
could go stale is checked by `crates/tailscale-mcp/tests/docs_are_current.rs`,
whose seven tests were each made to fail once — by doctoring the file they
guard and putting it back — rather than assumed to work.

**`docs/tools.md` is generated by the test that checks it** (Q119). One
function renders all 186 tools from `Registry::new(tools::entries()).metas()`:
an overview table of the 20 toolsets with their surface, tool count and the
presets each appears in, then a section per toolset with a row per tool giving
tier, version or platform note, and the first sentence of its description.
`UPDATE_DOCS=1 cargo test -p tailscale-mcp --test docs_are_current` writes it;
without the variable the same rendering is compared against the file, so a
tool added, renamed, retiered or moved between toolsets fails the suite. The
file's header names that command, so the fix arrives with the failure.

**`docs/configuration.md`** is the settings reference: a table of all 13
`TAILSCALE_MCP_*` variables with the flag each pairs with and its default, a
second table for the six credential variables, and the subcommands. It is
hand-written and mechanically constrained — the test takes the variable names
from `config::ENV_VARS` and the flag names from clap, and requires each to
appear in the table with a non-empty Default cell. A setting cannot be added
without documenting what it does when unset. Clap is walked to any depth, so a
flag added under `diagnose` or `tools` has to be named on the page too, though
those have no default to quote.

**`docs/errors.md`** is the envelope, the rule that callers branch on `code`
and not on the message, the fact that nothing in an error is a secret, all 14
codes with what each means and what to do about it, and the two refusals that
are not errors (a tool absent because of the tier, and `confirmation_required`).
The test compares the documented set against `ErrorCode` exactly: a code
neither missing nor invented.

**The README** carries what the tiers and presets are, with the nine
preset/tier counts and the three toolset counts in a table the test recomputes
from `Gate::unchecked` and `Preset::toolsets`; the
resources and prompts; the transports; the security section; and the
comparison. Nineteen per-toolset counts are written as links whose text is the
number and whose anchor is the toolset, so each one is both readable and
checkable, and the test parses them back out.

**The comparison table** has a row per capability across the three reference
implementations and this one, ending in tool counts — 1, 19, 102, 186. The
four deliberate exceptions are numbered below it: no configuration file, no
tool-schema resource, no OAuth resource-server mode (a deferral), and no
undocumented or out-of-set environment values. A test requires all four
phrases to be present, so the superset claim cannot quietly lose its
qualifications. One row's count is lower than YawLabs' — two of their tools
are aggregates over endpoints offered here one at a time — and the sentence
under the table says so rather than a tool being added to even the number up
(Q119).

**The security section** says what the tiers do (a tool above the tier is not
in the list; read-only by default; `confirm`; secrets never in an argument
list, a log or an error) and, at more length, what they do not: they are not an
authorization system and not a sandbox, a tier is a property of the server and
not the caller, permitting a tier permits every tool in it, the credential is
the real boundary, the local tools run as whoever runs the server, and read is
not harmless. It states that the server never escalates privileges — no
`sudo`, no elevation, no change to its own permissions — and names the four
tools that do write files and where each writes, so the claim is exact rather
than broad.
